CLAUDE.md — Regras do projeto (Gerenciador de Eventos / TCC)

Instruções gerais válidas para todo o repositório. Cada parte tem seu próprio CLAUDE.md com os detalhes técnicos:

Sempre rodar /using-superpowers Sempre rodar com Headroom ativo

Implementar issue / item do BACKLOG → SEMPRE pelo pipeline​

Qualquer tarefa do tipo "implementar a issue #N", "fazer o item N do BACKLOG.md", "resolver a issue X" passa obrigatoriamente pelo skill /implement-issue <N>, que orquestra os 4 papéis:

PapelQuem
Orquestradora sessão principal (conduz, roda testes, relata — não escreve código de feature)
Geradorsubagent code-generator
Revisorsubagent code-reviewer
Validador de specsubagent spec-validator

Definições em .claude/skills/implement-issue/SKILL.md e .claude/agents/*.md. Não implemente uma issue "na mão" na sessão principal pulando esse fluxo. O roadmap e a numeração das issues estão em BACKLOG.md (item N do backlog = issue #N+1 no GitHub).

Exceção: issues de Fase 0 puramente de ambiente (instalar Docker, preparar VM de carga) são passos manuais, sem diff — não precisam do pipeline.

  • Projeto/Backend/CLAUDE.md — API Spring Boot
  • Projeto/Backend/db/CLAUDE.md — banco PostgreSQL
  • Projeto/frontend/CLAUDE.md — app Flutter Web

Idioma​

Código, comentários, nomes, mensagens de commit, PRs e documentação em PT-BR. Manter o padrão do arquivo que você está editando.

Git​

  • Nunca commit ou push direto em main. Tudo entra por PR.
  • Implementação de issue (/implement-issue): branch Issue-N (uma por issue, criada no passo 3 com commit vazio + push). O PR entra só no passo 7, como draft; o passo 7.5 avalia as reviews do Copilot e do Gemini (findings relevantes vão pro usuário) e o PR sai do draft automaticamente quando os findings das duas foram tratados + validador CONFORME. Commits, pushes e atualização do PR nessa branch são automáticos. Mergear o PR Issue-N → main só quando o usuário pedir.
  • Fora desse fluxo (docs, config, etc.): só faça commit ou push quando o usuário pedir; antes de push, confirme.
  • Mensagens no estilo do histórico (Conventional Commits): feat:, refactor:, fix:, chore:, docs:. Uma mudança lógica por commit.
  • Feche a mensagem de commit com: Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
  • Corpo de PR termina com: 🤖 Generated with [Claude Code](https://claude.com/claude-code)
  • Nunca versione: Projeto/.env, **/target/, **/build/, dumps de banco, relatórios gerados (*-report-*.txt, database-export-*.txt), e o estado local do Claude Code (.claude/settings.local.json, .claude/*.local.*).
  • Versione .claude/agents/ e .claude/skills/ — são a estrutura de implementação do pipeline (ver acima), compartilhada com quem clonar o repo.

Segredos​

Projeto/.env contém credenciais reais (SMTP do Gmail, JWT_SECRET — sem uso desde a #36, chaves reCAPTCHA, senha do Postgres). Nunca imprima o conteúdo, cole em PR/issue, mande para serviço externo, ou registre em log. Para exemplos, use placeholders (<...>). O .env é lido por application.properties e pelo docker-compose.yml; código-fonte lê via variável de ambiente, nunca com valor hardcoded.

Os segredos do Supabase self-hosted ficam em Projeto/supabase/.env (gitignored, gerado a partir do .env.example pelo generate-keys.sh), com a mesma política: nunca imprimir, commitar ou registrar em log.

Código​

  • Siga o estilo e a estrutura do código vizinho. Não reformate arquivos inteiros.
  • Não troque de abordagem/stack sem alinhar com o usuário. Em especial: o backend usa JDBC puro de propósito (não Spring Data JPA); o schema mora em SQL nos scripts de init, não em @Entity. Não "migre" isso por conta própria.
  • Não edite artefatos gerados nem código legado marcado como tal (ex.: Projeto/frontend/blocoInteiro.dart é referência histórica, não o app ativo).
  • Mudou contrato de API, schema ou env var → atualize os 3 lados afetados (SQL / backend / frontend) e o CLAUDE.md da área.
