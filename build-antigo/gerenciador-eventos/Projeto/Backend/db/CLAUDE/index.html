CLAUDE.md — Banco de dados (PostgreSQL)

PostgreSQL 17 (imagem supabase/postgres), rodando em container. É a fonte de verdade do schema — não há migração via ORM. Leia também o CLAUDE.md da raiz e o de Backend/.

Container​

  • Definido em Projeto/docker-compose.yml (serviço db), imagem supabase/postgres:17.6.1.136 (a mesma do upstream fixado em Projeto/supabase/README.md). O antigo db/Dockerfile (postgres:16-alpine, pt_BR) foi removido na issue #18 e fica como fallback no histórico do git.
  • Pré-requisito: Projeto/supabase/.env precisa existir antes do up (o db lê os segredos do Supabase de lá; ver Projeto/supabase/README.md).
  • Host: localhost:5433 → dentro da rede Docker: db:5432. Container: gerenciador-db.
  • O usuário do app, a senha e o nome do banco vêm de Projeto/.env (POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB=meu_banco). Não commitar/imprimir. No container eles entram como APP_DB_USER/APP_DB_PASSWORD/POSTGRES_DB: o POSTGRES_USER do container fica o default da imagem (supabase_admin) — definir outro (ex. admin) quebra o init por peer auth. Por isso o db usa env_file: ./supabase/.env (segredos das roles internas do Supabase) e não mais ./.env.
  • Banco meu_banco, não postgres (decisão da issue #18): POSTGRES_DB=meu_banco faz a imagem criar o banco já com esse nome e rodar o init do Supabase nele (schemas auth, storage, extensions, pgbouncer). Assim o backend, o run-tests.sh e o gerador de carga (PGDATABASE=meu_banco) não mudam, e o tenant do Supavisor (#19) aponta para um banco só, que já tem o pgbouncer.get_auth e as tabelas do app (tenant criado em supabase/volumes/pooler/pooler-upsert.exs, #19).
  • Role do app: admin (de APP_DB_USER) é criada por supabase-app-init.sql como LOGIN sem superuser (menor privilégio) e vira dona do banco meu_banco — no PG15+ o schema public pertence ao dono do banco, então isso lhe dá CREATE no public e no banco (o TestSchemasTest cria um schema temporário). É dona das tabelas (os testes dão TRUNCATE como dona). Tarefa que exija superuser: docker exec gerenciador-db psql -U supabase_admin (trust no socket). Os init-scripts têm OWNER TO admin fixo, então POSTGRES_USER do Projeto/.env precisa continuar admin.
  • Locale/encoding: UTF-8, locale en_US.UTF-8 (ICU) da imagem — antes era pt_BR. Postgres 17.6 (antes 16).
  • Volumes: supabase-db-data (PGDATA; novo — o db-data antigo é PG16 e não sobe no PG17, fica órfão, não apagar) e db-config (/etc/postgresql-custom, guarda a chave do pgsodium).
  • Acesso: no socket do container só supabase_admin entra (trust); admin por socket falha (peer). Use -h localhost (127.0.0.1 é trust) ou TCP de fora com senha. O healthcheck usa pg_isready -U postgres -h localhost.

Inspeção visual (Supabase Studio)​

Com a stack no ar, o Studio fica em http://localhost:8000 (via Kong; login com DASHBOARD_USERNAME e DASHBOARD_PASSWORD de Projeto/supabase/.env). Table Editor → schemas identity (users, mywallet...; #36), catalog (event, eventpresenter; #35) e reservation (eventcap, walletevent...) mostram as tabelas do app; o SQL Editor roda consultas em meu_banco. Studio e meta conectam como supabase_admin, não como admin: é leitura/edição manual de apoio, o backend continua usando só JDBC. Detalhes e limites (sem GoTrue/PostgREST/Realtime/Storage/functions) em Projeto/supabase/README.md.

Como os init-scripts rodam (imagem supabase/postgres)​

O migrate.sh da imagem roda init-scripts/*.sql como postgres e depois migrations/*.sql como supabase_admin (um psql por arquivo, ordem lexical, no POSTGRES_DB). No compose:

  • Backend/db/supabase-app-init.sql → /docker-entrypoint-initdb.d/migrations/99-app.sql. O prefixo 99 roda depois de todas as migrations do Supabase. Ele cria a role do app, faz SET ROLE para ela (tabelas nascem com dono admin) e inclui com \i os scripts abaixo, montados read-only em /app-init (fora de /docker-entrypoint-initdb.d, para a imagem não rodá-los sozinhos com o dono errado). Script novo em init-scripts/ precisa de um \i lá.
  • supabase/volumes/db/roles.sql → init-scripts/99-roles.sql (senhas das roles internas) e supabase/volumes/db/functions-role.sql → init-scripts/98-functions-role.sql (cria a role supabase_functions_admin que o roles.sql altera; ver supabase/README.md).
  • supabase/volumes/db/_supabase.sql → migrations/97-_supabase.sql e supabase/volumes/db/pooler.sql → migrations/99-pooler.sql (issue #19): criam o banco _supabase (dono supabase_admin) e o schema _supavisor dentro dele. É o estado interno do Supavisor (tenants, métricas, schema_migrations do Ecto), não o schema do app: o app só usa o meu_banco. O 99-pooler.sql ordena depois do 99-app.sql (lexical) e termina com \c postgres; não depende dele. O Supavisor conecta no _supabase como supabase_admin e, no meu_banco, como o usuário do cliente (admin, via pgbouncer.get_auth, role pgbouncer do init do Supabase). O db não é mais o endpoint do backend em Docker: o backend usa supabase-pooler:6543 (ver Backend/CLAUDE.md, "Pooler"); 5433 do host e os testes seguem direto no db.

uid reciclado: TRUNCATE ... RESTART IDENTITY em identity.users (testes, limpeza entre blocos da carga) devolve o user_id a 1, e o JWT é validado sem estado (claim uid): um token emitido antes passaria a valer como o usuário novo com o mesmo id. Por isso, sempre que truncar identity.users fora de um teste unitário, apague também a chave de assinatura do volume identity-keys (com o identity parado) e reinicie o identity e o backend (o gateway guarda o JWKS em cache por até 24 h). O run-tests.sh apaga a chave ao fim da rodada; a limpeza entre blocos da carga (Projeto/carga/limpar-banco.sh) faz o roteiro inteiro.

Os scripts de init só rodam na PRIMEIRA criação do volume supabase-db-data (inclusive o _supabase/_supavisor do pooler; num volume antigo, recrie-o). Depois disso são ignorados. Para reaplicar do zero:

docker compose -f Projeto/docker-compose.yml down -v
docker compose -f Projeto/docker-compose.yml up -d --build

db/seed-data.sql popula dados de exemplo (ON CONFLICT DO NOTHING); rode manualmente: docker exec -i gerenciador-db psql -h localhost -U admin -d meu_banco < Projeto/Backend/db/seed-data.sql.

Modelo atual​

  • users — (schema identity desde a #36) PK user_id (identity). email, fone, user_name são UNIQUE e NOT NULL. Flags de papel: admin e Host — DDL declara Host boolean sem aspas (db/init-scripts/15-identity.sql; antes 02-users.sql), então o Postgres dobra o identificador para minúsculas: a coluna real é host, acessada sem aspas em SQL (igual isactive). Campos de MFA de reset de senha: password_reset_mfa_code, password_reset_mfa_expiration. created_at / updated_at com default.

    • Lido e escrito SÓ pelo serviço identity; qualificar sempre com identity. nas queries. Trigger trigger_create_wallet (AFTER INSERT): cria automaticamente a linha em mywallet. A aplicação nunca insere carteira à mão.

  • event — (schema catalog desde a #35) PK event_id. creator_id integer sem FK para users (referência solta; a Event_creator_id_fkey caiu na migração 20261026; quem confere o criador é o gateway). Migração a quente db/migrations/20261026-catalog-schema.sql: com o backend e o catalog parados e depois do pg_dump -n public (backup, aplicação e rollback no cabeçalho do arquivo); move event/eventpresenter e os streams catalog.event para o schema catalog. Lido e escrito SÓ pelo serviço catalog; qualificar sempre com catalog. nas queries. event_name UNIQUE, ead (bool), image_data bytea. Só metadados — capacidade/venda saíram daqui para eventcap.

    • version integer NOT NULL DEFAULT 0 (issue #28): é a projeção inline do stream catalog.event (ver Backend/CLAUDE.md, "Catalog em CQRS + Event Sourcing"); version = versão do último evento aplicado na linha e a versão esperada do próximo append (lida com FOR NO KEY UPDATE na transação do command; a projeção a grava com o valor do envelope). 0 = evento "pré-ES", sem stream. image_data não vem do log (blob fora do ES), e created_at/ updated_at são carimbos do banco: o replay compara event_id, creator_id, event_name, ead, address, event_date, description, version. event_id é GENERATED ALWAYS: a projeção insere com OVERRIDING SYSTEM VALUE (o id sai da sequence antes do append, é o streamId). Migração a quente: db/migrations/20261022-catalog-event-version.sql (idempotente; roda como supabase_admin; ADD COLUMN IF NOT EXISTS + backfill: cada evento com version = 0 ganha um EventCreated v1 no event_store (estado atual, sem imagem) + a linha do event_outbox, e só essa linha passa a version = 1). O backend recusa alterar/cancelar evento com version = 0 (erro "é pré-ES"): depois de carregar o seed-data.sql, que insere em event direto (aviso no topo do arquivo), reaplique a migração. Coberta por SchemaValidationTest, CatalogEventSourcingTest e o passo 8d do 99-tests.sql.

  • Schema reservation (issue #33, Fase 7 — o segundo schema por serviço): eventcap, walletevent, event_availability, idempotency_key e o event store do serviço (reservation.event_store/event_outbox/event_snapshot/projection_checkpoint, mesmo desenho de public) moram aqui e são lidos e escritos SÓ pelo serviço reservation. Nenhuma FK cross-schema — e nenhuma FK nas tabelas do schema (nem para users nem para event): o que ON DELETE CASCADE (eventcap) e ON DELETE RESTRICT (walletevent) garantiam virou chamada: o catalog remove o eventcap por DELETE /internal/eventcaps/{id}, que recusa (409) se existe walletevent do evento; e o gateway confere o evento antes de reservar (a carteira nasce com o usuário e o uid vem assinado no token). mywallet NÃO veio para cá (extensão 1:1 de users, FK + trigger): mora no schema identity (#36). event_store e cia. existem em cada schema de serviço: identity.* guarda identity.notification (congelado) e identity.user (#36); public.* ficou só com a infra da lib shared (testes); reservation.* guarda reservation.wallet; catalog.* guarda catalog.event (#35). Migração a quente: db/migrations/20261025-reservation-schema.sql (idempotente; docker exec -i gerenciador-db psql -h localhost -U supabase_admin -d meu_banco < ...; pare o backend e o reservation: lock_timeout de 5 s no SET SCHEMA) — move as quatro tabelas (dados e índices), derruba as FKs, cria o event store do serviço e move para ele os streams reservation.wallet que estavam no public.event_store (event_store com a global_position preservada, outbox pendente, checkpoint, snapshot) e reposiciona a sequence. Coberta por SchemaValidationTest (nos dois módulos), TestSchemasTest (o default do harness agora é public,notification,reservation) e o passo 9 do 99-tests.sql (apagar o evento não mexe no eventcap). Qualificar sempre com reservation. nas queries. A migração 20261022-catalog-event-version.sql (já aplicada em bancos existentes, editada na #33) passou a ler a capacidade de reservation.eventcap quando existe e senão de public.eventcap (SQL dinâmico): o comportamento depende do estado do banco, e continua idempotente nos dois (o fluxo "carregar o seed-data.sql e reaplicar" segue valendo).

  • eventcap — (schema reservation) agregado ISOLADO de capacidade. PK event_id, sem FK (antes → event ON DELETE CASCADE, até a #33). capacity (NOT NULL; CHECK eventcap_capacity_valid: -1 ou >= 1, 0 é recusado desde a #58, igual à regra lot_quantity >= 1 ou -1 do catalog), quant = vagas disponíveis (NOT NULL), buy_time_limit (timestamptz, nullable; timestamp até a #58), max_time_in_line (segundos, default 120).

    • capacity = -1 ⇒ sem limite de vendas (evento ilimitado); nesse caso quant = -1 também, o CHECK eventcap_quant_bounds (capacity = -1 OR 0 <= quant <= capacity) não restringe, e a reserva não passa pelo CAS — o serviço libera direto.
    • Limitado: reserva = UPDATE eventcap SET quant = quant - 1 WHERE event_id = ? AND capacity <> -1 AND quant >= 1 (CAS atômico; rowcount = 0 ⇒ lotado). Liberação = + 1 ... WHERE capacity <> -1 AND quant < capacity.

  • eventpresenter — (schema catalog desde a #35) apresentadores por evento. PK composta (event_id, presenter_name), FK → catalog.event ON DELETE CASCADE (a única FK do schema). Substitui o antigo campo único presenters.

  • mywallet — (schema identity desde a #36, junto com users: a FK e o trigger 1:1 não cruzam schema) PK user_id, FK → identity.users ON DELETE CASCADE.

  • walletevent — (schema reservation) inscrição/reserva N:N. PK composta (user_id, event_id). Sem FK (antes para users/event, ON DELETE RESTRICT, até a #33). status (confirmed|pending|expired| cancelled, default confirmed, CHECK) + expires_at (timestamptz, só quando pending; timestamp até a #58). NÃO é fonte de verdade (eventcap + CAS continuam sendo). Colunas: PK event_id, ativos (nº de reservas ativas: SlotReserved +1; ReservationExpired/ReservationCancelled −1; ReservationConfirmed 0), last_occurred_at (occurredAt do último evento aplicado: o maior visto) e applied_at (clock_timestamp() do commit do consumer; não now(), que seria o início da transação). A disponibilidade não é gravada: é calculada na leitura (eventcap LEFT JOIN esta tabela; CASE WHEN capacity = -1 THEN -1 ELSE GREATEST(capacity - GREATEST(COALESCE(ativos, 0), 0), 0) END; nunca lê eventcap.quant), então um evento sem reserva já tem disponibilidade e a mudança de capacidade vale na hora. O lag do último evento aplicado é applied_at − last_occurred_at. Sem FK para event e sem CHECK em ativos, de propósito: qualquer violação no consumer é SQLException, retentada sem limite pela política de erro, e travaria a partição; ativos pode ficar negativo (um Cancelled sem SlotReserved, de uma linha anterior ao ES) e a leitura trata ativos negativo como 0 (GREATEST(ativos, 0); sem isso a disponibilidade passaria da capacidade). O schema antigo (available, refreshed_at, created_at, FK com CASCADE, refresh por timer) saiu. Usa timestamptz (como todo instante do schema reservation desde a #58). PK global_position (bigint GENERATED ALWAYS AS IDENTITY: ordem de alocação, não de commit, então não serve de cursor), UNIQUE (stream_type, stream_id, version) (concorrência otimista: INSERT ... ON CONFLICT DO NOTHING, rowcount 0 = outra transação gravou a versão), CHECK (version >= 1). Regras ao alterar o schema​

  • Edite o .sql correspondente em init-scripts/. Se a mudança precisar valer para bancos já existentes (o volume não vai ser recriado), escreva também um script idempotente (ALTER TABLE ... IF NOT EXISTS, CREATE OR REPLACE) e rode manualmente via psql.
  • Reflita a mudança no repository JDBC correspondente do backend (nome de coluna, tipo, nullability) e ajuste SchemaValidationTest.
  • Atualize 99-tests.sql se a mudança afetar trigger/relacionamento.
  • Depois de mexer, valide com down -v + up e rode Projeto/Backend/run-tests.sh.
  • SQL sempre parametrizado no lado da aplicação; identificadores com maiúscula entre aspas.
