Decisões de arquitetura em vigor​

  • Back-end decomposto em microsserviços, Opção B (gateway, identity, catalog, reservation, notification, admission).
  • reservation = Capacity + Wallet no mesmo serviço (híbrido CAS + ES); split com saga é rodada futura (#46).
  • CQRS + Event Sourcing no escopo. ES em catalog e no lado wallet de reservation; eventcap/CAS fica relacional; identity CRUD; notification consumidor. Backbone Kafka-compatível (Kafka ou Redpanda); RabbitMQ para admissão; Redis para sinal de carga.
  • O experimento diferencial roda cedo e várias vezes (de-risking — feedback do orientador). Braço de controle "checar disponibilidade via read model defasado → oversella" roda 1º contra o monólito (Fase 2, read model sintético), depois re-roda a cada marco: monólito+ES (Fase 6) e distribuído (Fase 7). A série de 3 pontos é a contribuição rica.
  • Geração de carga em máquina/VM separada — números absolutos de latência/throughput são válidos, não só a contagem de corretude.

Prioridade: back-end e banco primeiro; front-end é prioridade baixa (só a issue #43).

Labels sugeridas: fase/0…fase/11, area/backend, area/banco, area/infra, area/frontend, area/eventos, area/carga, artigo, seguranca, bloqueado/docker.
