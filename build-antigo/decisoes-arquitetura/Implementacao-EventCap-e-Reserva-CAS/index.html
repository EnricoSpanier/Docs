  • Inscrição em dois passos: reservar (pending + expires_at) → confirmar.

Modelo de dados​

event (enxugada)​

Perdeu capacity, quant, buy_time_limit. Só metadados: event_id, creator_id, event_name, ead, address, event_date, description, image_data, timestamps.

eventcap (nova) — agregado isolado​

event_id (PK, FK→event ON DELETE CASCADE), capacity, quant (vagas disponíveis), buy_time_limit, max_time_in_line (segundos, default 120), timestamps.

  • CHECK eventcap_quant_bounds: capacity = -1 OR (0 <= quant <= capacity).
  • Regra de ilimitado: capacity = -1 ⇒ sem limite de vendas; quant = -1 também. Nesse caso o CAS não se aplica (a query traz AND capacity <> -1) e o serviço libera a reserva direto.
  • Reserva (evento limitado): UPDATE eventcap SET quant = quant - 1 WHERE event_id = ? AND capacity <> -1 AND quant >= 1 — rowcount = 0 ⇒ lotado.
  • Liberação: ... SET quant = quant + 1 WHERE event_id = ? AND capacity <> -1 AND quant < capacity.

eventpresenter (nova)​

(event_id, presenter_name) PK composta, FK→event ON DELETE CASCADE. Substitui o antigo campo único presenters (que nem era persistido).

walletevent (máquina de estados)​

Ganhou status (confirmed | pending | expired | cancelled, default confirmed, CHECK) e expires_at (só quando pending). Índice parcial idx_walletevent_pending_expires. PK segue (user_id, event_id); o insert virou UPSERT que revive linhas expired/cancelled.

Regras de negócio novas​

  • Capacidade obrigatória na criação: >= 1 (fixa) ou -1 (ilimitado).
  • buy_time_limit não informado ⇒ data do evento — aplicado no createEvent e no updateEvent (EventService.applyDefaults).
  • Reduzir a capacidade abaixo do já vendido é rejeitado (bate no CHECK → HTTP 400).

Fluxo de reserva (2 passos)​

  1. POST .../event-wallets → valida janela de compra + duplicidade, então numa transação: tryReserve (CAS) → se falhar, rollback + "Evento lotado"; se ok, grava walletevent pending com expires_at = now + max_time_in_line.
  2. POST .../event-wallets/confirm → pending → confirmed.
  3. DELETE .../event-wallets (cancelar) → cancelled + devolve a vaga, numa transação.
  4. ReservationExpiryService — @Scheduled (default 30s, @EnableScheduling em config/SchedulingConfig): varre pending vencidas e, por transação, expireIfStale (condicional, não pisa em confirmação concorrente) + release.

Compensação em caso de falha = rollback da transação (o decremento é desfeito automaticamente; não há compensação manual).
