Event Management System

Objetivo​

Sistema de gerenciamento de eventos (palestras, shows, workshops) com back-end em Java/Spring Boot + PostgreSQL e front-end em Flutter, usado como caso de teste real de uma estrutura de banco mais genérica: marketplace com estoque/capacidade isolado (qualquer item vendável com quantidade limitada — produto, vaga, assento, cota). A estrutura de dados não deve ficar presa ao domínio de eventos.

Estado atual​

  • Documentação original do sistema (back-end + front-end) mapeada a partir do README do projeto.

  • Padrão de arquitetura "estoque isolado" (CQRS+ES híbrido) definido em Backend-Architecture e aplicado ao caso real de capacidade de ingressos do evento.

  • Schema de banco (DBML) refinado em Database-Schema: EventCap isolado como agregado próprio, com UPDATE condicional atômico protegendo a invariante 0 <= quant <= capacity.

  • Decisão tomada: buy_time_limit fica em EventCap (junto de capacity/quant), não em Event — mantém toda a regra "posso vender?" coesa num único agregado, mesmo divergindo do README original.

  • Decisão de arquitetura documentada em termos genéricos de marketplace (não presa a eventos), com estrutura, vantagens, desvantagens e referências externas que ancoram a escolha.

  • Modo de alta carga definido em Architecture-Decision-Async-Checkout-Queue: RPM por evento (Redis) acima de um limiar X ativa (1) fila de admissão + worker pool e (2) reserva com expiração (WalletEvent.pending + expires_at). Virou o serviço admission.

  • Implementado no código (2026-09-01): eventcap e eventpresenter como tabelas isoladas, reserva por UPDATE condicional atômico, máquina de estados walletevent (pending → confirmed / expired / cancelled) com job @Scheduled de expiração, capacity = -1 = ilimitado, buy_time_limit default = data do evento. Detalhes em Implementacao-EventCap-e-Reserva-CAS. Verificado e mergeado em 2026-09 (issues #5–#9; PRs #55, #65, #66/#68, #70, #73) — estado atual em Roadmap-e-Issues.
