Escada de degraus: resultados de 2026-10-16

Rodada da issue #14 (limiar X), braço cas, com o host e o gerador descritos abaixo. É o X pré-pooler; a escada pelo pooler (X ≈ 78k RPM) está em Isolamento do pooler e escada X pelo pooler. Os números vêm dos CSVs em Projeto/carga/results/02-hikari/ (commit 5caac91 na branch Fase_2). O texto do artigo, com as ameaças à validade, está em docs/artigo/experimento-monolito.md, seção "Limiar X".

Resumo​

  • X de um evento disputado ≈ 97.000 RPM (~1650 reservas/s). O último degrau limpo é 96k.
  • O host nunca respondeu 5xx. Quando satura, ele fica lento: o p95 por janela de 30 s passa de 1 s.
  • O teto é a linha do eventcap, não a máquina. A escada manda 200 reservas seguidas para o mesmo evento, e o UPDATE do CAS nessa linha se serializa. Com a carga espalhada entre eventos, o host sustentou 140k RPM limpo.
  • Mais conexões e mais threads não ajudam. Postgres com 100 → 1000 conexões e Tomcat com 200 → 400 threads deixaram o teto igual e aumentaram a latência.
  • Com 60% de confirmação (versão realista), o host passa no X (p95 de ~216 ms em 97k).

Lições para as próximas rodadas​

  • O make setup-host sobe o Postgres com 100 conexões. Para outro valor, use make host-rpm MAX_CONN=<n> e confira com SHOW max_connections: a coluna max_connections do CSV é só um rótulo.
  • Acima de ~60k RPM, o gerador Windows esgota as portas efêmeras. Amplie como admin: netsh int ipv4 set dynamicport tcp start=10000 num=55535 (padrão: start=49152 num=16384).
  • 3000 VUs couberam em 16 GB de RAM; 4000 não.
  • Acima de ~140k RPM com a carga espalhada, é preciso um segundo gerador.
