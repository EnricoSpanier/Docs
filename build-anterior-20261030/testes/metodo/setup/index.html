Setup da máquina de geração de carga (issue #4)

Os passos 1–4 abaixo estão automatizados em Projeto/carga/ (setup-host.ps1, setup-gerador.ps1, rodar-teste.ps1; ver Projeto/carga/README.md). Este guia fica como referência manual e como lugar do registro do ambiente (seção 5). O runner oficial do experimento (matriz de N × repetições × lag, CSV + gráfico) está descrito em Projeto/carga/README.md.

Objetivo: uma máquina separada do host do sistema dispara a carga, para que latência e throughput absolutos sejam válidos (ver BACKLOG.md, "Decisões de arquitetura em vigor").

  • Host-alvo (SUT): a máquina que roda docker compose -f Projeto/docker-compose.yml up -d --build (backend :8081, Postgres :5433, frontend :8088).
  • Gerador de carga: a máquina nova. Não precisa de Docker, banco nem do Projeto/.env.

Nunca copie o Projeto/.env para o gerador (contém credenciais reais).

1. No host-alvo​

  1. Subir a stack e validar o baseline: docker compose -f Projeto/docker-compose.yml up -d --build.

  2. Descobrir o IP do host na rede local (ipconfig, adaptador em uso) e anotar: <IP_HOST>.

  3. Liberar a porta da API no firewall do Windows (somente rede privada):

    New-NetFirewallRule -DisplayName "TCC backend 8081" -Direction Inbound `
      -Protocol TCP -LocalPort 8081 -Action Allow -Profile Private

  4. Deixar a rede como Privada (Configurações > Rede). A 5433 (Postgres) só é aberta para a matriz do experimento (o gerador consulta confirmed/pending e o lag por psql remoto): regra TCC postgres 5433, perfil Privado, criada pelo setup-host.ps1 só com -GeradorIp <ip> e sempre restrita a esse IP (sem o parâmetro a 5433 continua fechada); remova ao fim do experimento com Remove-NetFirewallRule -DisplayName 'TCC postgres 5433'. A senha do Postgres vai para o gerador só pela variável de ambiente PGPASSWORD (ver Projeto/carga/README.md); nunca expor a 5433 para fora da LAN.

  5. Do gerador, http://<IP_HOST>:8081 deve responder (passo 4 abaixo).

  6. Para uma medição estável: ligar na tomada, plano de energia "Alto desempenho", fechar apps pesados e anotar CPU/RAM/disco do host na seção "Ambiente" abaixo.

2. No gerador de carga​

  1. Conectar na mesma rede do host, de preferência por cabo (Wi-Fi adiciona jitter).
  2. Instalar k6 (winget install k6 --source winget) ou, se preferir, JMeter/Gatling. Confirmar com k6 version.
  3. Clonar o repositório (para versionar os cenários em Projeto/carga/) e entrar na branch da issue. Sem .env.
  4. Mesmo plano de energia/desempenho do passo 1.6.

3. Medir a latência base de rede (para descontar depois)​

No gerador:

ping -n 100 <IP_HOST>
curl.exe -s -o NUL -w "connect=%{time_connect}s ttfb=%{time_starttransfer}s total=%{time_total}s\n" http://<IP_HOST>:8081/

Rodar 3 vezes em momentos diferentes e registrar min/média/máx e perda de pacotes. Esses valores são subtraídos das latências medidas nas rodadas da Fase 2.

4. Smoke test do k6​

Arquivo smoke.js (ajustar a rota para um endpoint GET público do backend):

import http from 'k6/http';
import { check } from 'k6';

export const options = { vus: 5, duration: '15s' };

export default function () {
  const res = http.get(`${__ENV.BASE_URL}/`);
  check(res, { 'status < 500': (r) => r.status < 500 });
}

Rodar: k6 run -e BASE_URL=http://<IP_HOST>:8081 smoke.js

Critério: sem erros de conexão e latência p95 coerente com a base medida no passo 3.

Observações das rodadas RPM (2026-10-04)​

  • Erros no backend durante a carga (docker logs gerenciador-backend, ~15:53Z): os jobs @Scheduled (atualização de event_availability e listagem de reservas expiradas) falharam com PSQLException: The connection attempt failed causada por java.net.BindException: Cannot assign requested address. Isso indica esgotamento de portas efêmeras (ou limite de conexões) na rota backend → Postgres, e não falha de lógica do CAS. O overselling continuou 0, mas os jobs de expiração/read model ficaram atrasados, o que explica reservas pending ainda ativas no verificador.
  • Ajuste: max_connections do Postgres elevado para 1000 (informado pelo operador; confirmar com SHOW max_connections e registrar as rodadas seguintes com esse valor). Atenção: BindException é falha do lado do cliente (portas efêmeras do backend), então subir max_connections pode não bastar; conferir também o pool do backend (tamanho máximo) e, se persistir, o range de portas do Docker/WSL. Comparar a próxima rodada RPM com a anterior (Rpm-903506, 300).
  • Rodadas com esse erro devem ser tratadas como saturação do ambiente, não como resultado de capacidade do sistema, até a causa ser isolada.
  • Rpm-904217 (max_connections=300 conforme o CSV do k6; o 1000 só foi aplicado depois): o backend ainda registrou 42 linhas de BindException/connection attempt failed nos últimos 30 min. Ou seja, subir max_connections não eliminou o erro, o que reforça a hipótese de portas efêmeras / pool do backend. Mantém-se como saturação do ambiente. (reservas_ativas 3414 vs pending 3413: as duas consultas do verificador não são atômicas e a carga ainda corria.)
  • Causa identificada (2026-10-04): o backend não tem pool de conexões. DatabaseConnection.getConnection() usa DriverManager.getConnection(...), ou seja, abre uma conexão TCP nova no Postgres a cada operação de repositório. Sob carga isso gera milhares de sockets em TIME_WAIT (medido no container do backend: tw 3363 logo após a rodada; faixa de portas efêmeras 32768–60999, ~28 mil) até esgotar as portas → BindException: Cannot assign requested address. Por isso subir max_connections não ajudou (o Postgres tinha só ~16 conexões ativas/ociosas). tcp_tw_reuse=2 já é o padrão do kernel (só loopback). As latências e a taxa sustentável medidas hoje refletem esse gargalo, não o CAS.
  • Correção possível (decisão do usuário, mudança de código de backend): introduzir um pool (HikariCP, via DataSource) mantendo JDBC puro, sem JPA. Alternativa só de ambiente: ampliar a faixa de portas efêmeras no container (sysctl net.ipv4.ip_local_port_range), que apenas adia o problema.
  • Ale-904991 (teste aleatório, PR #95): 110407 linhas de BindException/connection attempt failed no log do backend em 30 min (contra 42 na Rpm-904217), sem pool de conexões. Overselling 0, mas a rodada é de saturação do ambiente; comparar com a rodada pós-pool.

Evidência de esgotamento de portas (série de sockstat, backend, 2026-10-04 14:26–14:30)​

Série de sockstat (amostragem a cada 2 s de TCP: ... tw; não versionada: o results/02-hikari/sockstat.log só tem 5 amostras pós-pool, das 15:42):

  • Repouso: tw ≈ 14. Durante a carga: pico de 34.199 sockets em TIME_WAIT às 14:30:20.
  • A faixa de portas efêmeras do container é 32768–60999 = 28.232 portas. Como o destino é sempre o mesmo db:5432, o pico (> 28.232) confirma o esgotamento: sem porta livre, o connect() falha com Cannot assign requested address.
  • O tw só cai ~1.800 a cada 2 s depois do fim da carga (sockets expiram em ~60 s), então o backend fica sem conexões por minutos após cada rodada.
  • Conclusão: o gargalo medido nas rodadas de 10k RPM (4718 erros 5xx, ~31%) e na Ale-904991 (112.878 erros 5xx) é a falta de pool (#96), não o CAS nem o max_connections (1000 foi inútil: não mudou o 5xx). Overselling 0 em todas.

Achados e motivos​
  1. Causa raiz confirmada: o gargalo era a falta de pool, não o CAS nem o max_connections. DriverManager abria uma conexão TCP por operação → milhares de sockets em TIME_WAIT (pico 34.199 > 28.232 portas efêmeras) → BindException. Com o pool: 0 5xx e 0 BindException nas três rodadas; subir max_connections não tinha efeito antes, o que já apontava para a conexão por operação.
  2. Overselling 0 em todas as rodadas, antes e depois: o CAS é correto e o problema era de disponibilidade. Os números "a mais" (7501, 195.005) têm as explicações acima.
  3. Leitura bimodal (aberto): leitura p50 1,9 ms mas p95 456 ms e p99 492 ms. Suspeita, não medida por endpoint: GET /bff/events/search varre todos os eventos em memória. Não é efeito do pool. Follow-up fora do escopo da #96 (o N+1 do hydrate e o LIMIT/SKIP LOCKED são da #61).
  4. tw do sockstat pós-pool não foi medido durante a carga: o results/02-hikari/sockstat.log desta tarde tem só 5 linhas (15:42, tw máx. 6, em repouso) e não cobre as rodadas. O critério "tw de poucos milhares" não tem série própria; o proxy é BindException = 0 e 0 5xx.
  5. Default do pool 1000 só é seguro com max_connections alto: o db do docker-compose.yml padrão usa max_connections=100; fora do host de carga, reduzir por SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE. O minimum-idle 5 evita que cada contexto Spring (inclusive os de teste) segure 1000 conexões ociosas. O tamanho ideal do pool não foi explorado: com 100 VUs e latências de poucos ms, o pool nunca precisou chegar perto de 1000.
  6. Manhã e tarde não são perfeitamente comparáveis (banco zerado entre as baterias); a diferença é grande demais (5xx 112.878 → 0) para ser explicada por isso, então a comparação de latência é indicativa, não exata.
  7. Nenhum dos 3 testes finaliza vendas: todas as reservas ficam pending e depois expired; nenhuma chega a confirmed. Isso mede só o caminho de reserva (CAS), não a confirmação. Registrado para o próximo trabalho (testes com vendas efetivamente finalizadas).

Achados e motivos (vendas finalizadas)​
  1. Overselling 0 com vendas finalizadas. pending + confirmed ≤ capacidade em todas as rodadas. No aleatório as aceitas passam da capacidade (194.989 > 146.400) porque expired devolve a vaga e ela é revendida; as 116.744 confirmed (definitivas) ficam abaixo de 146.400.
