CLAUDE.md — Backend (API Spring Boot)

API REST do Gerenciador de Eventos. Spring Boot 3.5.7, Java 21, Maven (sem wrapper mvnw). Leia também o CLAUDE.md da raiz (regras gerais) e o de db/ (schema).

Rodar​

  • Via Docker (recomendado): docker compose -f Projeto/docker-compose.yml up -d --build backend — porta 8081, container gerenciador-backend. Sobe junto db, supabase-pooler e redpanda (o backend espera o broker ficar healthy); no Docker o backend fala pelo pooler (Supavisor), ver "Pooler" em Persistência, e com o broker em redpanda:9092 (SPRING_KAFKA_BOOTSTRAP_SERVERS).
  • Serviço notification (issue #32): docker compose -f Projeto/docker-compose.yml up -d --build notification — container gerenciador-notification, sem porta. Ver "Serviço notification". O backend NÃO depende dele.
  • Serviço reservation (issue #33): docker compose -f Projeto/docker-compose.yml up -d --build reservation — container gerenciador-reservation, API interna na :8082 só na rede gerenciador-net (sem porta no host). Ver "Serviço reservation". O backend depende dele (depends_on: reservation: service_healthy): sem ele não há reserva (o resto do monólito sobe).
  • Serviço stock (issue #47): docker compose -f Projeto/docker-compose.yml up -d --build stock — container gerenciador-stock, API interna na :8086 só na rede; entrypoint com.gerenciador.eventos.stock.StockApplication, stock/Dockerfile. Dono do eventcap (CAS) e do ledger de holds; o reservation depende dele (service_healthy, que por sua vez espera o one-shot stock-seek). Ver "Serviço stock e saga stock + wallet".
  • Serviço catalog (issue #35): docker compose -f Projeto/docker-compose.yml up -d --build catalog — container gerenciador-catalog, API interna na :8083 só na rede; entrypoint com.gerenciador.eventos.catalog.CatalogApplication, catalog/Dockerfile. O backend também depende dele (service_healthy); com ele parado /bff/events/** e a reserva respondem 503 (na reserva, um positivo de exists ainda no cache de 30 s do gateway deixa a reserva seguir). Ver "Serviço catalog".
  • Serviço identity (issue #36): docker compose -f Projeto/docker-compose.yml up -d --build identity — container gerenciador-identity, API interna na :8084 só na rede; entrypoint com.gerenciador.eventos.identity.IdentityApplication, identity/Dockerfile. Gera (1º boot) e guarda a chave de assinatura do JWT no volume identity-keys. O backend depende dele (service_healthy); com ele parado login, cadastro, /bff/users/** e /bff/my-wallets/** respondem 503, mas quem tem token válido segue reservando (JWKS em cache no gateway). Não sobe com a migração 20261028 pendente (PublicSchemaGuard). Ver "Serviço identity".
  • Serviço admission (issue #41): docker compose -f Projeto/docker-compose.yml up -d --build admission — container gerenciador-admission, API interna na :8085 só na rede; entrypoint com.gerenciador.eventos.admission.AdmissionApplication, admission/Dockerfile. Sobe junto o Redis (gerenciador-redis) e, desde a #42, o RabbitMQ (gerenciador-rabbitmq) e o reservation (depende dos três, service_healthy: o worker pool da fila de admissão chama o reservation). O backend não depende dele (o gateway faz fail-open): com ele parado a reserva segue síncrona, só sem a contagem. REDIS_PASSWORD, RABBITMQ_USER e RABBITMQ_PASSWORD são obrigatórias no Projeto/.env (ver "Serviço admission"). Sem datasource.
  • Local: cd Projeto/Backend && mvn -pl monolito -am spring-boot:run (ou mvn -pl notification -am spring-boot:run, mvn -pl identity -am spring-boot:run, mvn -pl reservation -am spring-boot:run) — precisa de um Postgres em localhost:5433 (e, para a reserva, do reservation em localhost:8082, o default de RESERVATION_SERVICE_URL; para login, do identity em localhost:8084, o de IDENTITY_SERVICE_URL). application.properties de cada módulo tem defaults de dev para as vars do .env, exceto MAIL_USERNAME/MAIL_PASSWORD do notification (sem default de propósito: não vai e-mail pessoal no código): para rodar o serviço local, exporte as duas.
  • Entrypoint do jar do monólito: com.gerenciador.eventos.Main (fixado em monolito/pom.xml e monolito/Dockerfile); o do notification: com.gerenciador.eventos.notification.NotificationApplication; o do reservation: com.gerenciador.eventos.reservation.ReservationApplication; o do identity: com.gerenciador.eventos.identity.IdentityApplication; o do admission: com.gerenciador.eventos.admission.AdmissionApplication.
  • Build da imagem: um Dockerfile por serviço (monolito/Dockerfile, notification/Dockerfile, reservation/Dockerfile, catalog/Dockerfile, identity/Dockerfile, admission/Dockerfile, stock/Dockerfile), contexto = Projeto/Backend/ (a raiz do multi-módulo); multi-stage — compila com maven:3.9.7-temurin-21 (-pl <serviço> -am), roda em temurin:25-jre.

Layout multi-módulo Maven — issue #32 (Fase 7)​

Projeto/Backend/ deixou de ser um módulo só: o pom.xml da raiz é o agregador (packaging=pom, parent spring-boot-starter-parent 3.5.7, dependencyManagement de shared, compiler e Checkstyle herdados por todos). Cada serviço é um módulo com o próprio jar e Dockerfile; o que é comum é uma lib.

  • Fronteira física: notification NÃO depende de monolito (só de shared) e não lê tabela do monólito; tem schema próprio (notification) e processo/imagem próprios. shared só leva o que mais de um serviço usa de verdade; o pacote Java continua com.gerenciador.eventos.shared[.events] (mesmos imports do monólito). Módulo novo (como a #33 reservation): novo diretório com pom.xml (parent backend, dep em shared), uma linha em <modules> do agregador, um <serviço>/Dockerfile copiado dos existentes (que passam a copiar também o pom.xml do módulo novo: o agregador exige o pom de todos) e um serviço no compose. reservation NÃO depende de monolito e o monólito não tem o código do reservation no classpath: a fronteira entre eles é o HTTP, e o que os dois compartilham é a lib reservation-client (contrato).
  • Testes de cada módulo ficam no próprio módulo. Os de shared.events (e o TestSupport) continuam em monolito/src/test, porque sobem o contexto Spring do monólito (Main) para exercitar a lib com Postgres e Redpanda reais. O reservation tem uma cópia enxuta do TestSupport (GlobalDbTruncator, TestSchemas com default reservation, EventsTestSupport) em reservation/src/test e ReservationTestSupport (ids de usuário/evento sem tabela de outro serviço). Os testes do monólito que tocam a reserva falam HTTP com o servidor falso TestSupport/FakeReservationServer (JDK HttpServer, estado em memória, sobe uma vez por JVM pelo LauncherSessionListener ReservationFakeSession, URL na propriedade de sistema reservation.service.url); o contrato cliente-servidor com o serviço REAL é o ReservationApiE2ETest do módulo reservation.
  • Backend/.mvn/maven.config existe para o Maven achar a raiz do multi-módulo (${maven.multiModuleProjectDirectory}, onde moram checkstyle*.xml) mesmo rodando de dentro de monolito/ ou notification/ (IDE); sem a pasta .mvn o Maven usa o cwd e o Checkstyle não acha a config.
  • Comandos: tudo na raiz de Backend/. mvn -pl monolito -am test (monólito + libs), mvn -pl notification -am test, mvn -pl reservation -am test, mvn -Dtest=ClasseTest -Dsurefire.failIfNoSpecifiedTests=false test (uma classe, em qualquer módulo). -pl X -am compila shared junto; sem -am o Maven procura shared no repositório local e falha.

Testes​

./run-tests.sh — sobe um container Maven na rede gerenciador-net, com --env-file ../.env (URL direta db:5432, sem passar pelo pooler), e roda mvn -fae clean test na raiz: o reactor inteiro (shared, reservation-client, stock-client, catalog-client, identity-client, admission-client, monolito, notification, reservation, stock, catalog, identity, admission; -fae = um módulo vermelho não esconde o resultado dos outros). Pré-requisito do stock (#47): o banco migrado (db/migrations/20261029-stock-schema.sql): o script ABORTA se reservation.eventcap ainda existe ou se faltam stock.eventcap/stock.hold, e se o gerenciador-stock (ou réplica com o label do serviço) estiver rodando; ao fim move os groups stock/stock-catalog para o fim dos tópicos. TEST_DB_NAME (default meu_banco) e ENV_FILE (default ../.env) permitem rodar os testes num banco isolado (o meu_banco fica no schema da R4); o banco novo é criado com os init scripts da worktree. Pré-requisito do catalog (#35): o banco migrado (db/migrations/20261026-catalog-schema.sql): o script ABORTA se public.event ainda existe ou catalog.event não existe (não aplica o 14-catalog.sql, que num banco não migrado criaria catalog.event vazia ao lado de public.event), e aborta se o gerenciador-catalog estiver rodando (o relay dele drenaria o catalog.event_outbox dos testes). Antes disso apaga target/surefire-reports sozinho, então o total do resumo reflete só os testes desta rodada — não precisa limpar na mão; os relatórios de todos os módulos são copiados para Backend/target/surefire-reports (nomes de classe únicos). Serviço identity (#36): o script aborta se o gerenciador-identity estiver rodando (docker stop gerenciador-identity; o relay dele drenaria o identity.event_outbox dos testes) e aborta se o banco ainda tiver public.users ou não tiver identity.users (migração db/migrations/20261028-identity-schema.sql pendente: backup pg_dump -h localhost -U admin --clean --if-exists -n public meu_banco, backend e identity parados; o script NÃO aplica o 15-identity.sql, que num banco não migrado criaria tabelas vazias ao lado de public.users; bancos novos já nascem certos). Banco verificado por db/migrations/verify-20261028-migration.sh (bancos descartáveis: sem o 15, com o 15 vazio, guardas, rollback, init completo). O monólito não tem mais public.users/mywallet/pending_verifications; o FakeIdentityServer (TestSupport, servido pelo LauncherSessionListener IdentityFakeSession, URL em identity.service.url) faz o papel do serviço nos testes do gateway. Chave do JWT e uid reciclado: os testes dão TRUNCATE ... RESTART IDENTITY em identity.users do meu_banco (o user_id volta a 1) e o JWT é validado sem estado pela claim uid; a chave de assinatura do identity de dev vive no volume gerenciador-eventos_identity-keys e sobreviveria à rodada, deixando um token antigo valer como o usuário novo com o mesmo uid. Por isso, no INÍCIO e ao fim da rodada (verde ou vermelha) o script apaga jwt-signing-key.json desse volume (identity e backend estão parados, pela guarda): o próximo boot do identity gera outra chave e todo token antigo vira 401 (relogar). O backend precisa ser (re)iniciado depois, porque o gateway guarda o JWKS em cache por até 24 h; parado durante os testes, ele sobe com o cache vazio. Se a remoção falhar, o script imprime o comando para rodar antes de subir identity e backend. Os testes do módulo identity usam uma chave de assinatura temporária por JVM e um reCAPTCHA falso (TestSupport/IdentityTestSession); a RECAPTCHA_SECRET_KEY real do .env nunca sai para o Google. Pré-requisito do notification (#32): o schema notification no banco (db/migrations/20261024-notification-schema.sql, num volume antigo; bancos novos já nascem com ele). Pare também o gerenciador-notification (docker stop gerenciador-notification): o relay dos testes do monólito publica em identity.notification e um notification vivo mandaria e-mail de verdade (SMTP real) para os endereços de teste; o script aborta com mensagem clara se ele estiver rodando. Ao fim da rodada (verde ou vermelha) o script move o consumer group notification para o FIM do tópico (docker exec gerenciador-redpanda rpk group seek notification --to end --topics identity.notification --allow-new-topics): os testes publicam ali (direto e pelo relay), e sem isso o próximo up do serviço (offset atrasado, ou group novo em earliest) mandaria e-mail REAL do Gmail para cada endereço de teste. Trade-off: um e-mail legítimo que estivesse pendente antes da rodada é pulado (aceitável em dev: o backend, e portanto o cadastro real, precisa estar parado para testar). Se o seek falhar, o script avisa e imprime o comando: rode-o ANTES de qualquer up do notification. Pré-requisito do reservation (#33): o schema reservation no banco (db/migrations/20261025-reservation-schema.sql, num volume antigo — move as tabelas de public e o stream reservation.wallet do event store; bancos novos já nascem com ele). Pare também o gerenciador-reservation (docker stop gerenciador-reservation): o relay, o consumer e a reconciliação dele disputariam o reservation.event_outbox, a projeção e o tópico catalog.event dos testes; o script aborta com mensagem clara se ele estiver rodando. Ao fim da rodada o script também move para o FIM dos tópicos os groups do serviço: reservation (projeção de disponibilidade, tópico reservation.wallet) e reservation-catalog (reconciliação do eventcap, tópico catalog.event) — a reconciliação, em particular, CRIARIA eventcap para ids de evento de teste (que se repetem depois de TRUNCATE ... RESTART IDENTITY). Exige os containers db e redpanda no ar (docker compose -f Projeto/docker-compose.yml up -d db redpanda; o script aborta com mensagem clara se faltar um): os testes batem num Postgres e num Redpanda reais. Pare o gerenciador-backend antes (docker stop gerenciador-backend): o relay e o consumer dele (ligados no compose desde a #28/#29) compartilham o meu_banco e drenariam o event_outbox dos testes (quebrando ReservationReplayTest e a prova de overselling do naive); o script aborta com mensagem clara se o container estiver rodando. O script passa SPRING_KAFKA_BOOTSTRAP_SERVERS=redpanda:9092 e EVENTS_CONSUMER_GROUP=gerenciador-eventos-test ao container de teste (group próprio: os testes nunca entram no group do backend vivo que consome do mesmo Redpanda).

Serviço admission e Redis (#41): os testes do contador usam o Redis REAL (container gerenciador-redis na rede gerenciador-net, REDIS_HOST=redis), então o script exige o gerenciador-redis no ar (REDIS_PASSWORD=<valor> docker compose -f Projeto/docker-compose.yml up -d db redpanda redis: o compose recusa subir sem a variável, que vem do Projeto/.env ou é exportada na shell só para o comando) e aborta se o gerenciador-admission estiver rodando (docker stop gerenciador-admission: ele contaria tentativas de teste no mesmo Redis). RabbitMQ (#42): os testes da fila e do worker usam o RabbitMQ REAL (container gerenciador-rabbitmq na rede gerenciador-net, RABBITMQ_HOST=rabbitmq), então o script exige o gerenciador-rabbitmq no ar (docker compose -f Projeto/docker-compose.yml up -d db redpanda redis rabbitmq; o compose recusa subir sem RABBITMQ_USER e RABBITMQ_PASSWORD, do Projeto/.env ou exportadas na shell só para o comando) e repassa RABBITMQ_USER/RABBITMQ_PASSWORD da shell com -e só se estiverem exportadas (senão valem as do --env-file), como a REDIS_PASSWORD. Os testes nunca usam as filas admission.* do serviço: cada classe monta admission.amqp.prefix=${admission.test.prefix}<sufixo> (o prefixo é sorteado por JVM no AdmissionTestSession, que também apaga as filas e exchanges no fim). Credencial: o container de teste recebe a REDIS_PASSWORD do --env-file (Projeto/.env) e, se a variável estiver exportada na shell, a da shell por cima (-e REDIS_PASSWORD, só nesse caso); a senha nunca vai na linha de comando do docker exec. FLUSHDB no gerenciador-redis no INÍCIO e ao FIM da rodada (verde ou vermelha): os ids de evento voltam a 1 com RESTART IDENTITY, e uma contagem de uma rodada antiga seria lida como carga da seguinte; o início aborta se o FLUSHDB falhar (senha errada), o fim só avisa e imprime o comando.

Schemas alvo: propriedade test.db.schemas (lista separada por vírgula, default public,notification,reservation,catalog,identity no monólito (o identity entrou na #36), só o schema do serviço no módulo de cada um (reservation, catalog, identity); vale também via env TEST_DB_SCHEMAS ou -Dtest.db.schemas=), usada também por SchemaValidationTest (table_schema = any(?)). Nomes validados por [a-z_][a-z0-9_]* (identificador não é parametrizável em SQL). O default só lista schemas do app (TestSchemas.DEFAULT): os schemas do Supabase (auth, storage, extensions...) vivem no mesmo banco e não podem ser truncados nem validados. Cada serviço extraído acrescenta o seu schema ao default (Fase 7: notification, reservation, catalog, identity). O GlobalDbTruncator do monólito também zera o estado do FakeReservationServer, do FakeCatalogServer e do FakeIdentityServer (os ids de evento voltam a 1 com RESTART IDENTITY). O run-tests.sh roda o mvn num container com env fixo (--env-file ../.env): para mudar test.db.schemas por ali, passe -e TEST_DB_SCHEMAS=... no docker run do script. Coberto por TestSchemasTest.

  • CatalogEventSourcingTest (issue #28; módulo catalog desde a #35; ver "Catalog em CQRS + Event Sourcing"): teste de replay do agregado Event (cria/edita/adiciona e remove apresentador/troca imagem/cancela vários eventos, reconstrói event/eventpresenter na sombra a partir do event_store e compara com a viva nas colunas comparáveis, sem image_data e sem carimbos; uma divergência provocada é detectada), tipos e versões contíguas de cada stream, payload sem PII/imagem e com valores calculados (o EventUpdated não carrega capacidade), evento pré-ES (version = 0) recusado, backfill da migração 20261022 aplicado 2× (um EventCreated v1, replay == viva), conflito de versão (transitório: o command repete; permanente: esgota as tentativas e não grava nada), 8 updates concorrentes no mesmo evento (log contíguo, sem versão perdida) e DELETE que falha por FK desfazendo o EventCancelled. EventUpdateAtomicoTest (issue #60): updatePolicy recusado (400, 409, 5xx) ou o fallback de criar o eventcap falhando não grava nada no catalog; falha na transação do catalog (spy na projeção) não deixa metadados nem apresentadores pela metade e o reservation já tem a capacidade nova (a janela documentada); sucesso com versões contíguas e replay == viva.

Inscrição em evento — reserva em duas fases (CAS)​

Desde a #47 o addLink é uma saga de duas transações curtas no reservation com um POST /internal/holds no stock entre elas (sem conexão aberta durante a chamada); o CAS vive no stock e removeLink/expiração só appendam o evento (a vaga volta pelo consumer do stock). A lista abaixo é a da #24/#29 (uma transação só); a atual está em "Serviço stock e saga stock + wallet".

Desde a #33 isto roda no serviço reservation (ver "Serviço reservation"): o gateway (EventWalletGateway) confere a carteira no monólito e o evento no serviço catalog (desde a #35, por HTTP, com cache positivo de 30 s) e chama a API interna dele por HTTP; o CAS, a guarda e o append continuam exatamente como abaixo, só que dentro do outro processo e do schema reservation. EventWalletService (módulo reservation):

  1. addLink (POST .../event-wallets): valida, checa janela de compra (eventcap.buy_time_limit) e duplicidade (existsActive = pending/confirmed), então numa transação (uma Connection, setAutoCommit(false) manual, não @Transactional): (a) reivindica a Idempotency-Key (IdempotencyKeyRepository.claim); (b) CapacityReserver.tryReserve(conn, eventId) (UPDATE condicional) → se false, rollback + IllegalArgumentException("Evento lotado"); (c) ReservationWriter.reservePending(conn, ...) grava walletevent como pending com expires_at = now + eventcap.max_time_in_line (UPSERT, revive linhas expired/cancelled; devolve a version); (d) appenda SlotReserved (#29); (e) commit.
  2. confirm (POST .../event-wallets/confirm): numa transação, pending → confirmed (expires_at = NULL) e append de ReservationConfirmed.
  3. removeLink (DELETE .../event-wallets): numa transação, um UPDATE condicional único (cancelIfActive: pending/confirmed → cancelled) e release + append de ReservationCancelled só se esse UPDATE afetou 1 linha — evita devolução dupla de vaga em cancelamento concorrente / corrida com o job. Reserva já cancelled/expired/inexistente ⇒ no-op silencioso (idempotente, sem evento).
  4. reservation/ReservationExpiryService — @Scheduled (a cada reservation.expiry.scan.ms, default 30s; @EnableScheduling em ReservationApplication, desde a #33): varre pending vencidas em lotes (#61; reservation.expiry.batch-size, env RESERVATION_EXPIRY_BATCH_SIZE, default 100): cada lote é UMA transação que seleciona com ORDER BY expires_at LIMIT n FOR UPDATE SKIP LOCKED (duas execuções concorrentes não pegam a mesma linha; o lock só vale dentro da transação) e, por linha e num savepoint, expireIfStale (condicional, não pisa em confirmação concorrente) + release + append de ReservationExpired (um por linha expirada; erro numa linha desfaz só ela, as outras seguem). Repete lotes até um voltar incompleto ou sem nenhuma expirada (linha que falha sempre não prende o job). Testes: ReservationExpiryBatchTest. O lote segura o lock das linhas de eventcap (a linha quente do CAS) que o release toca até o commit — por isso ele é limitado e configurável (o compose repassa RESERVATION_EXPIRY_BATCH_SIZE, default 100). A ordem de lock é inversa à da reserva (reserva: eventcap → walletevent; job: walletevent → eventcap), o que alarga a janela de deadlock: o Postgres aborta um dos dois, o savepoint da linha desfaz só ela e o job segue (a reserva abortada devolve erro ao cliente).

Reservation em event sourcing (híbrido) — issue #29 (ADR "Event-Backbone-Event-Store")​

eventcap + CAS ficam relacionais e síncronos, sem mudança. O lado wallet/order passa a ser event-sourced: o stream reservation.wallet (streamId = "userId:eventId", chave de partição = event_id, tópico = streamType) tem os eventos SlotReserved ({userId, eventId, expiresAt}, metadata {idempotencyKey}), ReservationConfirmed, ReservationExpired e ReservationCancelled ({userId, eventId}): ids e valores já calculados, nunca dado pessoal (o replay não chama now()). Código: reservation/ReservationEvents.

  • A versão sai da própria guarda. reservePending, confirm, cancelIfActive e expireIfStale fazem UPDATE/UPSERT walletevent ... SET version = version + 1 ... RETURNING version (coluna walletevent.version, 0 = linha anterior ao ES; a 1ª reserva do par é a v1). Sem SELECT separado: uma reserva concorrente com a expiração do mesmo par não lê versão velha (a linha fica travada até o commit, e o UPDATE reavalia a guarda depois do lock). Reservar de novo uma cancelada/expirada continua o mesmo stream (version segue).
  • Append só com rowcount 1, na mesma transação. Sem linha afetada (RETURNING vazio) não há evento. O append é o último comando antes do commit (EventStore.append, 1 statement com o INSERT do outbox). Conflito de versão no append (não deveria acontecer: a versão vem da guarda) = rollback: na reserva a resposta é "Vínculo já existente", como na corrida atual; em confirm/cancelamento/expiração é IllegalStateException (a guarda, a vaga e o evento voltam juntos). Os catch dessas transações pegam SQLException | RuntimeException (senão o finally setAutoCommit(true) comitaria a guarda sem o evento).

Idempotency-Key, invariante e compensação — issue #24​

  • Invariante: (1) reservas ativas (pending/confirmed) ≤ capacidade — só no braço cas (o CAS em eventcap e o CHECK eventcap_quant_bounds garantem; o naive oversella de propósito); (2) uma Idempotency-Key, por usuário, produz no máximo uma reserva (PK (user_id, idempotency_key)). Nenhuma outra requisição observa um estado em que a vaga foi debitada sem a reserva gravada (ou o contrário): tudo é uma transação.
  • Header Idempotency-Key em POST /bff/event-wallets, opcional e aditivo: sem ele, o servidor gera um UUID; a chave usada (gerada ou recebida) volta no header Idempotency-Key da resposta 201 (exposto no CORS). O corpo JSON e o contrato do Flutter não mudam (EventWallet.idempotencyKey é @JsonIgnore, só em memória). Máx. 255 caracteres (senão 400). A chave tem escopo por usuário (issue #129): a PK é (user_id, idempotency_key), então dois usuários podem usar a mesma chave sem colidir — cada um tem a própria reserva (claim e lookup usam o par).
  • Repetição (mesma chave, mesmo usuário e evento) devolve 201 com o resultado da primeira (status = pending, expiresAt salvo — mesmo depois de confirmar/cancelar a reserva) e não toca eventcap. Mesma chave, mesmo usuário e outro evento ⇒ 422 (IdempotencyConflictException; segue o rascunho IETF do header, que reserva 422 a "mesma chave, payload diferente"). Como o INSERT da chave bloqueia até a transação concorrente terminar, não há estado "em andamento" visível e portanto nenhum 409. Para reservar de novo o mesmo par depois de cancelar, use outra chave.
  • Só reserva bem-sucedida grava a chave: lotado / vínculo já existente fazem rollback e a mesma chave pode ser repetida depois.
  • Concorrência: duas requisições com a mesma chave serializam no INSERT ... ON CONFLICT DO NOTHING (a PK segura a 2ª até a 1ª dar commit/rollback). 1ª commita → a 2ª lê a linha salva e devolve o resultado (sem CAS). 1ª faz rollback → a 2ª segue como primeira. Antes da transação, se uma checagem falha (ex.: "Vínculo já existente" numa repetição sequencial), addLink consulta a chave e devolve o resultado salvo — a consulta extra só roda no caminho de erro.
  • Fronteira interna: CapacityReserver ("decrementar capacidade", EventCapRepository) e ReservationWriter ("gravar reserva", EventWalletRepository) são interfaces de reservation (não api); EventWalletService.addLink orquestra as duas na mesma Connection. É a costura do split futuro stock + wallet (#47).
  • Ponto de compensação: se a gravação da reserva (ou qualquer passo) falha depois do CAS, faz-se rollback da Connection — a vaga e a chave voltam juntas. No split futuro stock + wallet, o rollback deixa de cobrir os dois lados e a compensação vira um release (hoje EventCapRepository.release, o que removeLink/expiração usam, ainda fora da interface CapacityReserver) que terá de ser idempotente por chave no split.
  • Braço naive: a idempotência vale nos dois caminhos (a reivindicação da chave está na mesma transação curta; só o tryReserve é pulado). Na repetição sequencial a checagem do read model ("Evento lotado") falha como o "Vínculo já existente" e cai no mesmo desvio para o resultado salvo.
  • Retenção (issue #130): reservation/IdempotencyKeyRetentionService — @Scheduled (a cada idempotency.retention.scan.ms, default 10 min, env IDEMPOTENCY_RETENTION_SCAN_MS) apaga as linhas de idempotency_key com created_at mais antigo que idempotency.retention.hours (default 24h, a janela em que um retry do cliente faz sentido; env IDEMPOTENCY_RETENTION_HOURS). Passado o prazo, repetir a mesma chave deixa de ser reconhecida: vira reserva nova (ou "Vínculo já existente" se a anterior ainda estiver ativa). O DELETE roda em lotes de 1000 (CTE com LIMIT ... FOR UPDATE + junção por ctid), um por instrução em autocommit, repetidos até um lote voltar incompleto — não varre nem trava a tabela de uma vez. Filtra por created_at com o índice idx_idempotency_key_created_at. purgeExpired() é public e chamável direto (os testes o invocam; run-tests.sh estica o timer para 1h via env). A tabela não tem FK, então nada mais a apaga (não some com o evento).
  • Latência (ponto 2 da série, não medido): sob carga a rejeição ("Evento lotado") é o caminho quente, não só o sucesso. Custo novo por reserva bem-sucedida desde a #29, nos DOIS braços: +1 INSERT em event_store e +1 INSERT em event_outbox (num único statement, o último antes do commit, +1 ida ao banco) na transação do request, mais a escrita da linha e dos índices do event_store (PK + UNIQUE (stream_type, stream_id, version)) e do outbox, e +1 DELETE assíncrono do outbox no relay (tuplas mortas, autovacuum agressivo). Além disso, o confirm deixou de ser 1 UPDATE em autocommit e virou UPDATE ... RETURNING + append + COMMIT (a mesma ida de rede a mais por transição: cancelamento e expiração também appendam); a pré-checagem do naive virou eventcap LEFT JOIN event_availability (join por PK) no lugar da leitura de uma tabela. A rejeição ("lotado") não paga o append (rollback antes dele no cas; pré-checagem no naive). Custo por braço: no sucesso, cas e naive pagam 1 INSERT de chave (+1 ida ao banco, mais a escrita da linha e dos 2 índices: PK + created_at, #130). Na rejeição, o cas paga INSERT + rollback (tupla morta na idempotency_key e entrada morta nos dois índices, vacuum), pois o tryReserve roda depois do claim; o naive rejeita nas pré-checagens, antes da transação, e não paga nada (a consulta prévia da chave só roda com chave do cliente, nunca com a gerada). O ponto 2 da série compara os braços medidos com este código, não com as rodadas antigas.

Reentrega depois de um CAS que comitou é segura: o reservation devolve o resultado salvo pela chave (#129) e não toca o eventcap (provado contra o reservation REAL pelo IdempotencyKeyTest do módulo reservation e, ponta a ponta, pelo e2e/dry-run da #43; aqui, contra o falso).
