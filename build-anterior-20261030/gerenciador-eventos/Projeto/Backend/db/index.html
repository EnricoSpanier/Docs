Banco de dados (PostgreSQL)

PostgreSQL 17 (supabase/postgres, container gerenciador-db, banco meu_banco), com o schema em SQL, versionado aqui: não há ORM nem migração automática. Cada serviço é dono de um schema e nenhum lê tabela de outro; não há FK entre schemas. Regras completas, modelo de dados e decisões: CLAUDE.md. Visão geral do sistema: ../../../README.md.

Schemas por serviço​

SchemaDonoConteúdo
identityserviço identityusers, mywallet, pending_verifications; event store próprio (identity.notification, identity.user)
catalogserviço catalogevent, eventpresenter; event store próprio (stream catalog.event)
reservationserviço reservationwalletevent, idempotency_key (também o log da saga), projeção event_availability; event store próprio (stream reservation.wallet)
stockserviço stockeventcap (capacidade, CAS) e hold (ledger da saga); sem event store
notificationserviço notificationprocessed_event (idempotência do consumer)
publiclib sharedsó a infra de event store (event_store, event_outbox, event_snapshot, projection_checkpoint)

O admission não tem datasource (usa Redis e RabbitMQ). O usuário do app é admin (sem superuser, dono de meu_banco); o Supabase mantém os próprios schemas (auth, storage, extensions...) no mesmo banco e eles não são tocados.

Banco novo: init-scripts​

No primeiro up com o volume supabase-db-data vazio, o db roda supabase-app-init.sql, que cria a role do app e inclui, em ordem, os scripts de init-scripts/ (montados em /app-init):

OrdemScriptCria
111-event-store.sqlinfra de event store em public
212-notification.sqlschema notification
313-reservation.sqlschema reservation
414-catalog.sqlschema catalog
515-identity.sqlschema identity (com as funções e triggers da carteira)
616-stock.sqlschema stock
799-tests.sqlsuíte de sanidade em blocos DO (trigger, CAS, CHECKs, event store); apaga os dados de todas as tabelas do app, ver abaixo

Script novo em init-scripts/ precisa de um \i em supabase-app-init.sql. Os scripts só rodam na primeira criação do volume; para recomeçar do zero (apaga todos os dados e a chave do JWT):

docker compose -f Projeto/docker-compose.yml down -v
docker compose -f Projeto/docker-compose.yml up -d --build --wait

Pré-requisito: Projeto/supabase/.env existir (ver ../../supabase/README.md).

Banco existente: migrações​

migrations/ guarda os scripts idempotentes para quem já tem um volume antigo; aplique em ordem, só as que ainda faltam, a quente, com o usuário e o comando indicados no cabeçalho de cada arquivo. A maioria roda como supabase_admin (por isso as tabelas criadas levam OWNER TO admin explícito); 20260901 e 20260903 usam -U admin e a 20261020 copia o arquivo para o container com docker cp. Forma geral:

docker exec -i gerenciador-db psql -h localhost -U supabase_admin -d meu_banco -v ON_ERROR_STOP=1 \
  < Projeto/Backend/db/migrations/<arquivo>.sql

O cabeçalho de cada arquivo traz as precondições, o comando de backup, o de aplicação e o rollback. As migrações de schema de serviço exigem os serviços afetados parados e um backup pg_dump antes (o backup vale só até reabrir o tráfego e deve ficar fora do repo):

As migrações 20260901 e 20261026 a 20261029 vêm com um harness verify-<data>-migration.sh (+ .sql) que a prova num banco descartável, sem tocar em meu_banco (por exemplo migrations/verify-20261029-migration.sh); legacy-fixtures/ guarda o estado anterior usado por eles. As demais não têm harness.

Depois de truncar identity.users fora de um teste (limpeza manual, carga), apague também a chave do JWT do volume identity-keys e reinicie identity e backend: o user_id é reciclado e um token antigo passaria a valer para o usuário novo (Projeto/Backend/run-tests.sh e Projeto/carga/limpar-banco.sh já fazem isso).

Dados de exemplo e sanidade​

# dados de exemplo (INSERTs com ON CONFLICT DO NOTHING)
docker exec -i gerenciador-db psql -h localhost -U admin -d meu_banco < Projeto/Backend/db/seed-data.sql

Atenção com o 99-tests.sql: ele dá TRUNCATE ... RESTART IDENTITY CASCADE em todas as tabelas do app (identity, catalog, reservation, stock e a infra de event store). No primeiro up de um volume novo ele roda no init e é inofensivo; não o rode contra um banco com dados que você queira manter. Para executá-lo à mão, use um banco descartável criado com os init-scripts atuais. É também o que o TEST_DB_NAME do run-tests.sh espera: o banco precisa ser criado antes (o script não o cria, só o usa) e, nele, os testes é que dão o TRUNCATE.

O seed-data.sql insere eventos direto na tabela, sem passar pelo catalog: depois dele, reaplique a 20261022-catalog-event-version.sql (idempotente) para criar o stream de cada evento. A alternativa por API é POST /bff/seed, que só existe com SEED_ENABLED=true (override de carga; ver ../../README.md).

Inspeção visual: Supabase Studio em http://localhost:8000 (login com DASHBOARD_USERNAME e DASHBOARD_PASSWORD de Projeto/supabase/.env).
