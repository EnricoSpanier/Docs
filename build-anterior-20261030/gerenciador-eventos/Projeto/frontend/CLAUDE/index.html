CLAUDE.md — Frontend (Flutter Web)

App web em Flutter, servido como estáticos por Nginx em produção. Leia também o CLAUDE.md da raiz (regras gerais) e o de Backend/ (contrato da API).

Rodar​

  • Via Docker: docker compose -f Projeto/docker-compose.yml up -d --build frontend — Nginx na porta 8088 (container :80), container gerenciador-frontend.
  • Build local: flutter build web --release --dart-define=API_BASE_URL=<url> --dart-define=RECAPTCHA_SITE_KEY=<key>
  • Dev: flutter run -d chrome --web-port=3000 --dart-define=API_BASE_URL=http://localhost:8081 (aponta direto pro backend, sem o proxy do Nginx — precisa do backend rodando em :8081 com CORS liberado pra origem do flutter run, ver Backend/CLAUDE.md). --web-port=3000 bate com o default de CORS_ALLOWED_ORIGINS (#133); outra origem (127.0.0.1, IP da LAN) exige acrescentá-la a CORS_ALLOWED_ORIGINS no Projeto/.env.
  • Sem lockfile versionado; flutter pub get resolve pelo pubspec.yaml. Flutter 3.19.6 / Dart SDK >=3.3.0 <4.0.0 (ver Dockerfile).

Como fala com o backend​

  • Superfície HTTP única sob /bff/** (issue #78) — todas as chamadas seguem o mesmo padrão: Uri.parse('${AppConfig.apiBaseUrl}/bff/...'). Não existe mais divisão entre chamada relativa e absoluta: é sempre esse padrão, o que muda é só o valor de apiBaseUrl.
  • AppConfig.apiBaseUrl (API_BASE_URL, --dart-define, String.fromEnvironment) tem default vazio (''). Vazio ⇒ path fica relativo (/bff/...), resolvido contra a origem da página — em produção (docker-compose.yml não passa mais args.API_BASE_URL, usa o default do Dockerfile) isso cai atrás do proxy do Nginx em :8088. Setado (ex.: flutter run --dart-define=API_BASE_URL=http://localhost:8081) ⇒ aponta direto pro backend, sem Nginx (uso em dev). Mudar exige rebuild da imagem — não é runtime.
  • Nginx faz proxy de /bff/ → backend:8081/bff/ SEM rewrite/strip (nginx.conf): o path chega igual no backend, ex. /bff/users/login → /bff/users/login. O nginx.conf é um template da imagem oficial (/etc/nginx/templates, envsubst só de BACKEND_*): o upstream vem de BACKEND_UPSTREAM (default backend:8081, no Dockerfile); o override docker-compose.autoescala.yml (#111) o troca por lb:8081 (HAProxy na frente das réplicas do gateway). Contrato do app (porta e path) inalterado.
  • JWT: ApiAuth.jsonHeaders() injeta Authorization: Bearer <token>. O token fica em memória (ApiAuth.token) e, se persistido, em SharedPreferences (jwt_token). main.dart tenta GET ${AppConfig.apiBaseUrl}/bff/users/me no boot pra restaurar a sessão; token inválido é limpo. "Lembrar de mim" também cacheia email/password em SharedPreferences.
  • Reserva em duas fases e modo fila (contrato da #43, consumido pela tela da #44): POST /bff/event-wallets só reserva: 201 traz a reserva pending com expiresAt; com o evento acima de 80% de X responde 202 Accepted (headers Idempotency-Key e Retry-After: 1, expostos no CORS; corpo {"status":"queued","eventId":n,"idempotencyKey":"..."}; nenhuma reserva ainda). GET /bff/event-wallets/admission?idempotencyKey=<chave> (autenticado) devolve 200 {"status":"queued"|"pending"|"rejected"|"timed_out", "eventId", "idempotencyKey", "expiresAt"?, "reason"?}; 404 = chave inexistente ou de outro usuário, 400 sem chave, 503 admission fora. O POST também pode dar 400 (texto: "Evento lotado", "Vínculo já existente"), 422 (chave usada em outro evento) e 429 (limite/fila cheia). A confirmação é sempre POST /bff/event-wallets/confirm (200; 400 com "Reserva expirada..." ou "Nenhuma reserva pendente..."). O widgets/painel_reserva.dart (embutido na telaInscricaoEvento, no lugar dos botões) faz tudo isso:
    • Fluxo: "Reservar vaga" -> 201 vai à contagem regressiva mm:ss + botão "Confirmar inscrição" (o sucesso é o de antes: AppModals.showSuccess e volta à MainScreen); 202 mostra "aguardando confirmação" e consulta o estado até pending (mesma contagem), rejected (mostra o reason) ou timed_out ("Tentar de novo"). Prazo vencido (contagem a 0, ou /confirm com 400 de reserva expirada) -> "Reserva expirada" + "Reservar de novo". /confirm com 400 "Reserva já confirmada" conta como sucesso. O reservation só varre pending vencido a cada ~30 s: um "Reservar de novo" que volte 400 "Vínculo já existente" a partir de "expirada" mostra "a reserva anterior ainda está sendo liberada" no painel (sem modal). Cliques repetidos em reservar/confirmar são ignorados com um POST em voo.
    • expiresAt é UTC sem offset: o servidor serializa um LocalDateTime do relógio do container (UTC, sem TZ no compose), ex. 2026-10-28T18:30:00.123456. DateTime.parse direto daria a hora local do navegador (3 h errada em UTC-3), então parseExpiresAtUtc lê string sem Z/offset como UTC. A contagem usa o relógio do navegador: relógio de cliente errado desloca o prazo mostrado (o servidor continua sendo quem decide no /confirm).
    • Consulta: Timer cancelável (cancelado no dispose, e respostas de rodada antiga são descartadas) no intervalo do Retry-After (1 a 5 s; padrão 1 s), no máximo kLimiteConsultas = 60 (60 s, acima do TTL da fila de 30 s); ao estourar, "Tentar de novo". 404 oferece refazer; 503/erro de rede seguem tentando dentro do limite ("conexão instável"); 401 pede novo login.
    • Chave de idempotência: "Tentar de novo" depois de timed_out repete o POST com a MESMA chave (header Idempotency-Key = a do corpo do 202) e pode voltar 201 ou 202. Refazer depois de pending expirado ou de rejected é um POST novo, SEM chave (a antiga repetiria o resultado guardado).

Estado e UI​

  • Estado global via provider — HomePageData (ChangeNotifier) guarda dados do usuário, nome do site e listas de evento. Atualize via notifyListeners() após login/edição.
  • Feedback ao usuário sempre pelos helpers de telas/modals.dart, não ScaffoldMessenger cru — mantém cor/estilo consistentes.
  • Material Design (uses-material-design: true). Textos em PT-BR.
  • Datas: intl + helpers/date_input_formatter.dart para máscara de input.

reCAPTCHA v3​

widgets/recaptcha_widget.dart + config/recaptcha_config.dart. A site key entra por --dart-define=RECAPTCHA_SITE_KEY; o backend (serviço identity) valida o token contra a Google. Site key é pública, mas mesmo assim não hardcode — mantenha via dart-define.
