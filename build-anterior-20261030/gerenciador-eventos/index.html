Gerenciador de Eventos

Link Video Final de 2025​

Sistema web de gerenciamento de eventos (palestras, shows, workshops): cadastro com verificação por e-mail, login, criação e edição de eventos por hosts, e reserva de vagas em duas fases (reserva com prazo, depois confirmação) sem overselling mesmo sob concorrência alta. O projeto é o objeto de um TCC: o back-end nasceu como um monólito Spring Boot e foi decomposto em serviços, com CQRS + event sourcing no catálogo e na reserva, para medir o efeito de cada decisão de arquitetura sob carga.

O front-end é um app Flutter Web; o back-end é Java 21 / Spring Boot 3.5 com JDBC puro (sem JPA: o schema mora em SQL) sobre PostgreSQL 17 (supabase/postgres, self-hosted), com Redpanda (backbone de eventos), Redis e RabbitMQ (admissão de reservas).

"Rede" quer dizer só dentro da rede Docker gerenciador-net, sem porta no host. As libs shared (infra de event store, relay e consumer) e reservation-client, stock-client, catalog-client, identity-client, admission-client (contrato HTTP de cada serviço) não são serviços. Infra de apoio no compose: db (supabase/postgres 17, porta 5433 no host), supabase-pooler (Supavisor), Studio (127.0.0.1:8000, via kong, mais meta), redpanda, redis e rabbitmq. Diagramas e saltos entre serviços: docs/arquitetura/fase7-servicos.md; decisões: docs/adr/README.md.

Pré-requisitos​

  • Docker com Compose v2. Maven, JDK e Flutter não são necessários no host: build e testes rodam em container.
  • Projeto/supabase/.env: segredos do Supabase, gerados por script (ver Projeto/supabase/README.md, "Gerar os segredos"). Sem ele o db não sobe.
  • Projeto/.env: credenciais do app. Não vai para o git e nunca deve ser colado em issue, PR ou log. A lista dos nomes de variável que o compose e o run-tests.sh exigem (inclusive as obrigatórias, sem default: sem elas qualquer docker compose recusa) está em Projeto/README.md, seção "Pré-requisitos".
  • Portas livres no host: 8081, 8088, 5433 e 8000.

Subir a stack​

# tudo, reconstruindo as imagens e esperando todos os serviços ficarem healthy
docker compose -f Projeto/docker-compose.yml up -d --build --wait

# estado e logs
docker compose -f Projeto/docker-compose.yml ps
docker compose -f Projeto/docker-compose.yml logs -f backend

Testes​

  • Back-end (todos os módulos, com Postgres, Redpanda, Redis e RabbitMQ reais): Projeto/Backend/run-tests.sh, depois de subir só a infra e parar os serviços (eles dividiriam banco, broker e Redis com os testes); o passo a passo e o docker stop estão em Projeto/Backend/README.md. Atenção: a rodada dá TRUNCATE ... RESTART IDENTITY nas tabelas do app do meu_banco (apaga os dados da stack real; para isolar, use TEST_DB_NAME com um banco criado antes), apaga a chave do JWT (todo token antigo vira 401) e move consumer groups do Redpanda; os efeitos estão no mesmo README.
  • Stack inteira (e2e): Projeto/e2e/run-e2e.sh sobe tudo num project temporário gerenciador-e2e, isolado da stack real e sem e-mail de verdade (captador Mailpit), exercita cadastro, evento, reserva, confirmação, a saga e a fila, e derruba só esse project no fim. MANTER=1 mantém o project; E2E_SLIM=1 usa as imagens enxutas. Precisa de python e openssl no host, além de Projeto/.env e Projeto/supabase/.env.
  • Front-end: lint, teto de tamanho de arquivo e flutter test rodam no container do SDK Flutter; o comando está em Projeto/frontend/README.md.
